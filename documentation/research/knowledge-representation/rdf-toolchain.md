# RDF toolchain (rdflib, Oxigraph, pySHACL, graph-keeper)

> **TL;DR** If we add a graph, it should be this stack: YAML → Turtle via **rdflib**, constraints via **pySHACL**, SPARQL via rdflib (small) or **pyoxigraph** (faster, persistent), and ongoing curation via the existing **graph-keeper** skills. Everything is plain text in git and fully inspectable. Assess it, and build it only when [graph-decision.md](graph-decision.md) triggers fire.

## What it is
- **rdflib 7.6.0** (2026-02-13, BSD-3-Clause): pure-Python RDF with parsers and serializers (Turtle, JSON-LD, …) and SPARQL 1.1 ([PyPI](https://pypi.org/project/rdflib/), accessed 2026-09-25).
- **Oxigraph** (Apache-2.0 OR MIT): a Rust RDF store on RocksDB, with SPARQL 1.1 Query/Update/Federation, preliminary RDF/SPARQL 1.2 support, and Python bindings (`pyoxigraph`), JS/WASM and a CLI server. The README warns it is "in heavy development" and that query evaluation "has not been optimized yet" ([GitHub](https://github.com/oxigraph/oxigraph), accessed 2026-09-25).
- **pySHACL 0.40.1** (2026-07-28, Apache-2.0): validates RDF against SHACL shapes, with optional RDFS/OWL-RL inference, a CLI and an Oxigraph backend option ([PyPI](https://pypi.org/project/pyshacl/), accessed 2026-09-25).
- **graph-keeper** (local Claude skills): tends a Turtle graph in git (`graph/core.ttl` vocabulary with term status, confirmed data in `graph/*.ttl`, tentative triples in `staging/`) under explicit human ratification, with the rules "reuse > specialize > coin" and "heal by equivalence, not deletion".

## Why it matters for gentext
It is the only graph option that keeps DR-0005 intact: text in git, derived indexes, readable diffs. SHACL is the right tool for cross-registry rules that JSON Schema can't express, and SPARQL answers multi-hop questions without ad-hoc joins.

## How it would fit
```
gentext export-rdf   → build/graph/library.ttl  (derived, gitignored or committed as snapshot)
pyshacl -s schema/shapes.ttl build/graph/library.ttl   → M7 report section
gentext sparql 'SELECT …'                           → rdflib or pyoxigraph
```
- Namespaces: `schema:` (Organization, Project, MonetaryGrant), `skos:` (terms and topics), `prov:` (derivation, `wasDerivedFrom` for lineage), plus one small `gt:` namespace for our types (Chunk, Variant, Fact).
- Shapes can be generated by LinkML if we adopt it ([frontmatter-schema-validation.md](frontmatter-schema-validation.md)).
- graph-keeper operates on a separate `graph/` for purely semantic relations and reads `library.ttl` as context.

## Strengths
- Standards-based, portable and diffable, with no server needed at our size (rdflib in memory handles tens of thousands of triples easily *(typical, not benchmarked here)*).
- There is already team tooling (graph-keeper) and experience with it.

## Weaknesses / risks
- Two representations to keep aligned (YAML and TTL), which the exporter mitigates by always being derived.
- RDF and SPARQL are unfamiliar to non-technical colleagues. Claude can write the queries, but humans must be able to read the results.
- Oxigraph is pre-optimization and under heavy development. rdflib is enough at our scale.

## Verdict rationale
Assess: this is the right stack when a graph becomes necessary, but not yet needed for the pilot.
